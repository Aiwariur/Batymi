## Краткий договор prompt

Короткая версия договора prompt v7:

1. Уточни долгосрочную сдачу и доступность, включая названный будущий срок.
2. Установи, собственник ли собеседник, и запиши подтверждённый тип контакта в этом же ходе.
3. Уточни согласие сотрудничать и запиши статус согласия в этом же ходе.
4. Подтверди актуальную месячную цену с валютой и минимальный срок аренды; не повторяй подтверждённое.
5. Сохрани прочие добровольные факты, но не делай вид и ЖК условиями квалификации; после ответа на встречный вопрос задай не более одного следующего вопроса, а после qualified отправь короткий финал без внутренних статусов или неподтверждённых обещаний.

Модель получает компактный снимок настоящей CRM и последние 50 CRM Interaction в хронологическом порядке с автором, WhatsApp instance и message/Interaction ID. История привязана к последнему фактическому исходящему вопросу, включает первое сообщение CRM и текущий входящий batch ровно один раз; повторы дедуплицируются по ID, другой WhatsApp instance не подмешивается. Действия ограничены listing IDs, доступными данному контакту; selectedListingId сохраняется при ограниченной repair-попытке. При нескольких объектах без выбора модель сначала уточняет адрес и ничего не записывает.

Рабочий цикл: **план модели → безопасные разрешённые CRM-действия → результаты действий и обновлённый CRM-снимок → финальный ответ модели**. Для плана и финального текста используются отдельные structured-вызовы; при отсутствии записей второй вызов не нужен. При ошибке записи ответ не утверждает успех; допускается ограниченная recovery-попытка/повтор CRM, затем задача остаётся видимой как ошибка. После успешного qualified отправляется один финальный ответ; следующий входящий сохраняется в Interaction, но не вызывает LLM и не отправляется.

В последующих реальных прогонах v5/v6 обнаружились лишние процедурные формулировки в финале; v6 убрал внутреннее «заявка квалифицирована» и обещание передачи менеджеру без такого действия, сохранив ответ на языке владельца. Проверка v6 также выявила повторный вопрос о будущей доступности в финале и потерю selectedListingId при repair-попытке нескольких квартир. В v7 prompt уточнён для короткого финала без повторного вопроса; bounded repair теперь получает предыдущий сырой план и конкретную ошибку, сохраняя выбор Listing. Для одного Listing разрешены статусы agreed, qualified, disagreed; для нескольких — agreed и disagreed, чтобы действие qualified не пересекало область всего контакта. Это ограничение области действия, а не кодовый выбор следующего вопроса. Успешность CRM writes и критерии статуса не ослаблялись.

- P0 «Вид на море»: ответ реального v7 acceptance — «Спасибо, вид на море зафиксировал. Подтвердите, пожалуйста: актуальна ли цена 900 USD в месяц?». CRM сохранила добровольный факт вида; Listing остался в agreed, qualified не выставлен этим ответом. Scripted v7 replay legacy-сценария отдельно сохранил допустимый вопрос о ЖК: «Спасибо, вид на море записал. Подскажите, в каком ЖК квартира?».
- «Свободна с декабря»: сохранена заметка «Свободна с декабря»; availability_status=unknown. Ответ не выдумывает день или год.
- В сценарии нескольких квартир первый ответ уточняет адрес и оставляет оба объекта без записей. После выбора Kobaladze 12 CRM diff ограничен выбранной квартирой, типом контакта и заметкой о ручной проверке: L101: agreed/owner, rental_terms.price=850 USD, минимум 12 мес.; L202: agreed/owner, rental_terms без изменений (900 USD, минимум не задан). У Listing 202 rental terms остаются прежними; Глобальный Contact.contact_type=owner; оба Listing имеют crm_status=agreed, qualified не выставлен. В agent_notes записана причина проверки менеджером.
- Отказ, риелтор и уже сданная квартира завершаются соответствующими ветками без ложной квалификации; после последнего исходящего менеджера агент пропускает обработку (model calls 0, send 0).
- В crm-write-failure первая запись set_contact_type возвращает HTTP 503. Этот attempt не отправляет ответ; обработка ставится на retry. Повторная запись HTTP 200 проходит до дальнейших условий и одного ответа. Все попытки и статусы приведены раздельно в таблице.
- В сценарии повторного webhook проверена защита от второго send. Отдельные integration-тесты owner-checkpoint-recovery проверяют восстановление отправленного intent без LLM/CRM/send и потерянный ответ CRM после совершённого status transition без повторной записи статуса.

## Что именно было проверено и границы результата

Родительский прогон проверок: npm test — 172/172, включая отдельную проверку Redis; npm run typecheck и npm run build успешны; Python contract suite — 39 passed и 2 существующих deprecation warnings. SQLite contract tests для Flask route проверены отдельно; production PostgreSQL не проверялась.

Реальная здесь только LLM-часть acceptance: вызовы configured OpenAI-compatible endpoint с alias из метаданных JSON. CRM — локальный HTTP-double с синтетическими фактами. В кодовом пути использованы RealCrmClient и CrmReplySender, но endpoint и transport-подмены не подключены к production CRM, GreenAPI или WhatsApp. Входящее сообщение для replay вручную заранее внесено в synthetic CRM; proxy заменён mock. Поэтому настоящий webhook/proxy integration не доказан. Тест takeover покрывает сообщение менеджера, попавшее в загруженное окно истории. Случай, когда оно ушло за пределы последних 50 записей после новых входящих без новых исходящих, отдельно не проверялся; бессрочную остановку по такому архивному сообщению этот прогон не доказывает.

Защищённая трасса run реализована на AES-256-GCM с настройкой retention по умолчанию 7 дней. В этой среде RUN_TRACE_KEY не настроен, поэтому долговременная трасса отключена. Наличие production key, приватного volume и ACL доступа не подтверждено.

Реальный исторический плохой случай с correlated webhook/run/Interaction IDs недоступен. Локальная репродукция старой версии показывает воспроизводимый defect path, но не доказывает причину конкретного production-разговора. В production изменений не внесено: commit, push и deploy не выполнялись. Выпускной gate остаётся контролируемый end-to-end разговор на тестовом номере после deploy с проверкой health/CRM-записи и тишины на следующем входящем сообщении. Этот отчёт не утверждает, что production исправлен или работает.

Чужие ранее изменённые файлы видео, parser, catalog и другие отчёты оставлены без изменений.
