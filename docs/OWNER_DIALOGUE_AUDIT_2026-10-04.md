# Batymi: разбор диалога с собственником и план упрощения

Дата: 4 октября 2026 года. Объект анализа: локальные исходники `Batymi` на коммите `30ad59a`, арендная CRM в соседнем каталоге этого проекта, действующие n8n-гайды и исторический export workflow. Это заключение об архитектуре и воспроизведённом локальном поведении. Реальные продакшен-переписки, конфигурация сервера и доставка конкретного сообщения в этом разборе не проверялись. Код приложения не менялся.

**Для реализации использовать [новое задание](OWNER_DIALOGUE_REPAIR_HANDOFF_2026-10-04.md).** Оно заменяет рекомендации этого аудита о том, кто выбирает следующий вопрос: разговор ведёт модель, код проверяет только допустимость записи в CRM и доставку.

## Короткий вывод

Проблема не сводится к тому, что языковая модель «не умеет пять вопросов». В Batymi ответ модели одновременно является текстом для человека и программой изменения CRM. После модели программа дополнительно толкует весь диалог регулярными выражениями, отбрасывает или добавляет факты, меняет статус и иногда полностью заменяет ответ. При этом смысл некоторых правил определяется по тексту **предыдущего вопроса**, а не по явно сохранённому состоянию анкеты. Это даёт несколько независимых источников решений об одном и том же следующем шаге.

**Доказанный дефект:** если в статусе `agreed` спросить одновременно вид из окон и ЖК, а собственник ответит только «Вид на море», локальный `finalizeAgentResponse` самостоятельно ставит `qualified` и вместо следующего вопроса «А в каком ЖК квартира?» отправляет завершающую фразу. Пример воспроизведён после `npm run build` на текущем коде. Он прямо нарушает желаемую последовательность диалога, даже когда модель предложила правильный следующий вопрос.

Рекомендуемая цель: **один явный объект состояния разговора и один вычислитель следующего вопроса**. Модель извлекает смысл сообщения и формулирует короткий ответ; переход стадии, набор недостающих данных и разрешение записи в CRM решает одна небольшая функция над подтверждёнными фактами. Защиту транспорта и адресации объявления сохранить.

## Что было задумано в n8n

Исторический `n8n/Batumi-Rental-Ai.json` удалён из текущего checkout, но найден в Git-истории исходного проекта `SS.GE!` на коммите `8beb7261fb76926f8957bd692d59e0688558029d` (родитель коммита удаления `91977dc`). Его содержимое с credentials не выводилось и не переносилось. По метаданным workflow: 39 узлов, включая заметки; два `AI Agent`, один `OpenAI Chat Model` (`gpt-4o`), общая `Simple Memory` с окном 15, прямые HTTP-tools для чтения объекта, установки статуса и типа контакта; `update_deal_info` подключён ко второй фазе. Снаружи были GreenAPI, Redis-буфер, аудио и отправка сообщения. То есть исходная схема тоже имела инфраструктурную сложность, но сам агент в каждом ходе видел историю, вызывал нужный инструмент и писал ответ, без нынешнего второго «собеседника» на регулярных выражениях.

Действующие файлы `n8n/N8N_AGENT_PROMPT.md` и `N8N_AGENT_AGREED_PROMPT.md` уже дорабатывались после раннего export, поэтому это **не точная копия первоначального промпта**. Но их устойчивое продуктовое правило ясно: читать сказанное человеком, принять несколько фактов из одного сообщения, не спрашивать известное снова и работать с конкретным `listing_id`. Текущий CRM-outreach фактически спрашивает только об актуальности долгосрочной аренды (`src/routes/whatsapp.py:713-722`), поэтому короткое «да» отвечает именно на актуальность, пока агент отдельно не спросит о сотрудничестве. Старый n8n-гайд местами предполагает, что первое сообщение уже спрашивало и о сотрудничестве (`n8n/N8N_AGENT_PROMPT.md:30-45`); нынешний шаблон CRM это опровергает.

## Как сообщение обрабатывается сейчас

```text
GreenAPI webhook
  → проверка instance / подписи / типа сообщения
  → асинхронный proxy сырого webhook в CRM (Interaction)
  → Redis pending + debounce → BullMQ job + lock
  → текст batch / транскрипция
  → GET CRM listings по телефону, фильтр AI-менеджера
  → фаза из crm_status; prompt из CRM-снимка + история Redis
  → один LLM call: { reply, actions, stopConversation }
  → groundRentalFacts / groundedRentalActions / finalizeAgentResponse
  → applyGates → несколько последовательных CRM HTTP-записей
  → outbound intent → CRM /api/chat/reply → GreenAPI
  → запись ответа Batymi в Redis-историю
```

Опорные места: `src/webhooks/greenapi.routes.ts:87-148`, `src/buffer/message-buffer.ts:13-74`, `src/conversation/conversation.service.ts:653-921`, `src/agent/agent.ts:93-154`, `src/agent/actions.ts:37-120`, `src/crm/reply.sender.ts:35-80`.

Транспортные части решают реальные задачи: дедупликацию входящих, защиту от гонок, выбор того же WhatsApp-инстанса, безопасный повтор отправки, адресацию конкретного объявления. Они не являются причиной доказанного ниже диалогового дефекта. Удаление Redis/BullMQ или перенос всего обратно в n8n не исправит логику следующего вопроса само по себе.

### Где живёт состояние

| Источник | Что содержит | Ограничение |
|---|---|---|
| CRM `Contact` и `Listing` | статус контакта, тип, поля аренды конкретной квартиры | статус `agreed`/`qualified` слишком крупный, чтобы знать, какой вопрос уже задан и на какой ответили |
| Redis history Batymi | собственные входящие и отправленные им ответы; максимум 30 сообщений, TTL 30 дней по умолчанию | первая рассылка CRM и ручные ответы менеджера не загружаются в историю модели; после TTL и отсечения контекст исчезает (`src/config/env.ts:30-31`, `src/buffer/redis-store.ts:300-316`) |
| Текст последнего ответа | код ищет в нём слова «вид», «ЖК», вопросительный знак и т. п. | стиль фразы становится скрытым переключателем состояния (`src/conversation/conversation.service.ts:116-180`, `536-583`) |
| Текущий ответ модели | свободный `reply` и действия записи CRM | код может изменить оба после модели (`src/conversation/conversation.service.ts:463-650`) |

`runAgent` отправляет модели system prompt, Redis history и текущий batch (`src/agent/agent.ts:98-106`). Он не читает CRM `Interaction`/`/api/chat/history`; CRM-клиент Batymi умеет читать объявления, но не полную переписку (`src/crm/crm.client.ts:40-57`, `123-136`). При этом prompt вставляет пример исходного сообщения, а реальный шаблон рассылки может быть изменён настройкой `whatsapp_message_template`. Так возникает риск неверно истолковать короткое «да» или повторить вопрос после ручного вмешательства менеджера. Это архитектурный риск; для конкретного случая нужна фактическая трасса.

## Найденные дефекты и противоречия

### P0 — досрочное закрытие разговора после частичного ответа

`phaseTwoWasAsked` возвращает true, когда **любой** прошлый ответ агента с вопросительным знаком содержал и «вид», и «ЖК» (`src/conversation/conversation.service.ts:176-180`). `hasPhaseTwoAnswer` возвращает true уже по одному слову «море» (`:246-249`). Когда обязательные поля аренды в CRM уже заполнены, условие в `finalizeAgentResponse` считает этого достаточно для автоматического `qualified` и заменяет ответ модели финальной фразой (`:569-583`). Наличие ещё не полученного ЖК не учитывается. Одновременно prompt требует не закрывать диалог после первого частичного ответа на пакет (`src/agent/system-prompt.ts:232-255`).

Локальный опыт: `agreed`, owner, цена 900 USD/месяц, квартира доступна, минимум 12 месяцев; предыдущий вопрос «Какой вид из окон? В каком ЖК квартира?»; входящее «Вид на море»; модель предлагает записать вид и спросить ЖК. Выход функции: запись вида **плюс** `set_crm_status=qualified`, `stopConversation=true`, ответ «Спасибо, всё необходимое ... зафиксировал». Это установленное поведение кода, а не оценка качества модели.

### P0 — неверная доступность и потеря срока «с декабря»

`availabilityFact` видит слово «свободна» и возвращает `available` без учёта будущего месяца (`src/conversation/rental-facts.ts:37-44`). `groundRentalFacts` оставляет `lease_terms_notes` только если текст заметки буквально содержится в сообщениях владельца (`:171`), а отдельный `available_from` намеренно не записывается (`src/agent/system-prompt.ts:117`). Локальный опыт с «Свободна с декабря» и предложенным моделью `lease_terms_notes: "Доступна с декабря"` дал только `availability_status: "available"`; информация «с декабря» исчезла. Это опаснее стилистики ответа: CRM может считать объект доступным уже сейчас.

### P1 — три автора следующего вопроса

Prompt просит модель выбрать следующий пункт (`src/agent/system-prompt.ts:146-255`); `agreedPhaseFallback` строит собственный список из CRM и того, **задавался ли** вопрос, считая заданный вид/ЖК как будто он больше не нужен (`src/conversation/conversation.service.ts:129-173`); `finalizeAgentResponse` может заменить ответ или закрыть разговор (`:561-627`). Система не хранит `asked`, `answered`, `unknown`, `declined` как разные состояния поля. Поэтому модель, fallback и статусный gate могут прийти к разным выводам. Этим объясняется, почему очередной локальный regex-патч помогает одному скриншоту, но не делает пять ходов предсказуемыми.

### P1 — анкета спорит с целью короткого разговора

Фаза 1 запрашивает собственника, сотрудничество и арендные условия; фаза 2 снова строит «одну пачку» из вида, ЖК и недостающих обязательных условий (`src/agent/system-prompt.ts:146-255`). Сохранённый LLM-прогон в `reports/dialogue-quality-check.md` показывает после согласия **пять пунктов в одном сообщении**: вид, ЖК, срок, депозит/предоплата, комиссия. Модель потом справляется с подготовленным ответом, но собственнику легко ответить только на часть. Комиссия, депозит, вид и ЖК не входят в текущий gate `qualified` (`src/agent/gates.ts:47-72`), однако prompt и тесты уделяют им приоритет, как если бы они были обязательными.

### P1 — статус `qualified` не равен готовности публикации

Gate Batymi проверяет цену, валюту, `month`, `rent_long_term`, `available` и минимальный срок (`src/agent/gates.ts:57-72`, `307-330`). Он не проверяет `contact_type=owner` в самом переходе: локальный вызов `applyGates` допустил `qualified` для `contact_type=potential_owner`, если CRM уже имела `agreed` и базовые поля. CRM-гейт публикации дополнительно требует owner/cooperation proof, время подтверждения доступности и пригодные фотографии (`../src/utils/rental_readiness.py:154-200`). Следовательно, финальное «Готовим публикацию» при `qualified` ещё не доказывает, что объект можно публиковать. Разделить «разговор собрал минимум» и «публикация разрешена» в состоянии и формулировках.

### P1 — тесты проверяют части системы, а не реальный путь сообщения

`npm test -- --reporter=dot`: 172 passed, 2 skipped; `npm run build`: успешно. Значительная часть conversation-проверок удостоверяет состав фикстур и работу evaluator (`tests/conversations/scenarios.test.ts:35-60`); mock LLM работает по regex, а не как реальная модель (`src/agent/llm.provider.ts:98-222`). Отдельный сохранённый LLM-прогон вызывает модель и локальный guard, но **не** CRM, GreenAPI и WhatsApp (`scripts/check-dialogue-quality.ts:51-93`). Все эти проверки полезны, но не опровергают P0-примеры и не доказывают качество конкретной продакшен-переписки.

### P2 — нет воспроизводимой истории конкретного решения

Есть `runId`, `jobId`, этапные логи и небольшой debug recorder (`src/conversation/conversation.service.ts:658-664`, `src/observability/debug-recorder.ts:9-41`). При `LOG_MESSAGE_CONTENT=false` тексты обычно не попадают в логи; raw output модели возвращается из `runAgent`, но в рабочем pipeline используется только `result` (`src/conversation/conversation.service.ts:813`). Из этого нельзя восстановить точную цепочку «что увидела модель → что предложила → что отбросили проверки → что было записано → что ушло в WhatsApp». Это мешает лечить именно те случаи, которые раздражают пользователя.

## Рекомендуемая архитектура разговора

1. **Один канонический снимок перед ходом.** По выбранному `listing_id` собрать CRM-факты и реальную переписку: последнее исходящее сообщение CRM, ответы собственника, сообщения менеджера, ответы Batymi. Сохранять `last_question_key` явно, а не искать смысл в сгенерированной фразе. Если разговор взял менеджер, ставить явный pause/handoff.
2. **Один маленький dialogue state.** Для каждого поля хранить `value`, `source_message_id`, `confidence`, `status` (`unknown`, `asked`, `confirmed`, `declined`, `needs_review`). Контактная роль и согласие остаются у `Contact`, условия — у конкретного `Listing`. `asked` не равен `confirmed`. Состояние обновлять только после успешной записи CRM или явно помечать pending/retry.
3. **Модель как интерпретатор, а не диспетчер всей системы.** На вход дать короткий CRM-снимок, точную историю и последний вопрос. На выходе запросить `intent`, извлечённые факты с фрагментом исходного сообщения, ответ на встречный вопрос и признак неопределённости. Не давать модели одновременно решать status, перечень HTTP-действий и окончательный текст. Для неоднозначного «да» использовать `last_question_key`; при сомнении спросить уточнение.
4. **Одна функция перехода.** Она сливает подтверждённые факты с CRM, выбирает ровно один ближайший обязательный пробел и разрешает адресные записи. Сначала актуальность; затем роль; затем сотрудничество; затем недостающие цена/валюта/месячный период, доступность и минимальный срок. Уже названные несколько фактов записывать одним ходом. Необязательные депозит, комиссия, вид и ЖК собирать, когда человек их сообщает или когда есть реальная продуктовая необходимость, но не держать диалог бесконечно.
5. **Ответ короткий и проверяемый.** Модель может естественно сформулировать выбранный системой вопрос и ответить на встречный вопрос, но не выбирать другой пункт анкеты. Перед отправкой проверить, что ответ не обещает несуществующих клиентов/публикации, не повторяет подтверждённое и содержит один понятный следующий вопрос, если разговор продолжается. При сбое модели отправить заранее заданный вопрос из state, а не запускать вторую, конкурирующую анкету по regex.
6. **Сохранить защиту интеграции.** Оставить проверку вебхука, Redis/BullMQ, идемпотентность, lock, outbound intent, `listing_id`, допустимые CRM-статусы и отправку через тот же instance. Убрать из диалогового слоя распознавание стадии по словам «вид/ЖК» в собственном тексте и автоматическое закрытие после любого частичного ответа.

Пример целевого короткого пути: CRM спросила, сдаётся ли квартира → «Да, свободна» → «Вы собственник?» → «Да» → «Готовы сотрудничать?» → «Да, 900 долларов, минимум год, депозит месяц» → записать все четыре факта и спросить **только реально недостающий обязательный пункт**, если он есть; иначе поблагодарить и передать на проверку публикации. Встречный вопрос собственника получает прямой ответ до следующего вопроса. Если он сообщает «с декабря», сохранить будущую дату/словесное условие и **не** ставить доступность «сейчас».

## Порядок реализации и критерий приёмки

1. **Сначала трасса и контракт.** Зафиксировать 10–15 реальных обезличенных цепочек и ожидаемые CRM-поля после каждого хода. Для каждого run сохранять ссылки на входящее сообщение, CRM-снимок, версию prompt/model, сырой и разобранный ответ модели, причины решений gate, HTTP-результаты и outbound ID. Доступ к персональным данным ограничить; задать срок хранения и возможность удаления. Это постоянное хранилище run, не рост RAM контейнера.
2. **Сделать state reducer и воспроизводимые тесты.** Обязательные случаи: простое «да» на разные предыдущие вопросы; несколько фактов одним сообщением; частичные ответы на список; транслит; исправление цены; «с декабря»; два объявления; вопрос о комиссии; ручной ответ менеджера; отказ; возврат после паузы; истечение Redis history. Для каждого хода проверять **текст следующего вопроса, факты, `listing_id`, статус и отсутствие нежелательных записей**. Отдельным регрессионным тестом зафиксировать P0-пример «Вид на море».
3. **Прогнать один и тот же корпус через текущую и упрощённую логику.** Измерять долю завершённых без повторов, ложные `qualified`, потери фактов, неверные CRM-поля, число ходов и ручных исправлений. Прохождение mock-тестов считать лишь базовым gate; обязательны вызовы настроенной модели и тестового CRM без реальных собственников.
4. **Включать поэтапно.** Сначала shadow-режим на копиях входящих данных без отправки и без CRM-записей; затем ограниченный AI-менеджер/instance с ручным контролем; лишь после сверки полных трасс — остальной трафик. Не перенаправлять реальный GreenAPI webhook и не делать тестовую отправку собственнику ради проверки.

**Критерий готовности первоочередной задачи:** на согласованном наборе реальных и синтетических переписок агент без вмешательства проходит короткий разговор, не повторяет подтверждённое, не завершает диалог после частичного ответа, сохраняет каждый названный факт по правильному Listing, не объявляет будущую доступность текущей, корректно отвечает на встречные вопросы; каждое решение можно восстановить по run. После развёртывания это нужно подтвердить на конкретных продакшен run и фактической доставке, а не только тестами.

## Границы уверенности

- P0-сценарии и допуск `qualified` без owner проверены локальными вызовами кода после успешной сборки; это факты о текущем checkout.
- Сохранённый `reports/dialogue-quality-check.md` показывает один ранний вызов настроенной LLM; он не является статистикой или подтверждением текущего провайдера на сервере.
