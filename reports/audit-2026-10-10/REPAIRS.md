# Batymi: исправления после ревизии 10 октября 2026

## Задача и итоговая последовательность

Нужно получить первичное решение собственника о сотрудничестве с агентством
долгосрочной аренды. Если предложение или объект непонятен, коротко объяснить
и повторить один вопрос. После решения дальнейший разговор ведёт менеджер.

1. CRM проверяет пригодность объявления для первичного обращения, выбирает
   активную WhatsApp-линию и сохраняет исходящее сообщение с маркером
   `cooperation_outreach:v1:<listing_id>`. Источник линий — CRM.
2. GreenAPI присылает webhook в Batymi. Сырой webhook долговечно ставится в
   очередь доставки CRM; сообщение собственника — в Redis buffer той же линии
   и контакта. Дубли одного webhook не создают повторных сообщений.
3. После debounce worker блокирует диалог, читает Contact/Listings и историю
   CRM. Терминальный статус, ручная пауза либо ответ менеджера/телефона
   прекращают автоматизацию до вызова модели или транскрибации.
4. Текст читается напрямую, каждое аудио получает собственную расшифровку.
   CRM-заглушка «🎵 Аудио» заменяется сохранённым текстом при сборке истории.
   Все даты сравниваются в миллисекундах.
5. Одиночное «да/нет» после двух первоначальных вопросов вызывает один вопрос
   о сотрудничестве. Ответ «да/нет» на точный вопрос, сформированный программой,
   завершает диалог без LLM. Неизвестный объект не получает статус автоматически.
6. Для остальных реплик semantic_v3 определяет только intent, language,
   выбранное объявление и цитату текущей реплики для терминального решения.
   Ответ и разрешённое действие формирует код. Произвольных reply/actions
   от модели больше нет; фактические адрес и ссылка берутся из CRM.
7. Явное согласие → agreed; отказ сотрудничать → disagreed; квартира уже
   сдана/недоступна → listing_removed; агент → realtor. Это решения по Contact
   в существующем контракте CRM. applied:false не считается успешной записью.
   Срок или цена квартиры сами по себе не означают согласие. Явное согласие
   вместе со сроком аренды остаётся согласием.
8. «Что предлагаете?» получает объяснение помощи со сдачей и вопрос о
   сотрудничестве. «Какая квартира?» — адрес/внешнюю ссылку и тот же вопрос.
   RU/EN/KA/русский транслит имеют проверенные короткие варианты ответа.
9. Просьба человека/вопрос об ИИ и необходимость согласовать комиссию или
   условное сотрудничество создают ручную паузу. Собственнику ничего не
   обещается. Менеджер видит запись проверки в CRM и получает однократное
   частное Telegram-уведомление при настроенном канале.
10. Ответ отправляется через CRM с сохранённым outbound intent. Подтверждённая
    отправка после сбоя только завершает историю/ack; повторно не отправляется.
    Неоднозначный результат требует ручной проверки.
11. Каждую минуту ограниченное восстановление возвращает безопасную недавнюю
    работу в очередь. Временные ошибки повторяются с durable backoff; после
    пяти неудачных циклов требуется менеджер. Сообщения старше суток и
    небезопасные отправки автоматически не переигрываются.

## Закрытые дефекты

|---|---|
| F01: вопрос о смысле предложения вызывает вечную паузу | explain_service + фиксированное объяснение |
| F02: согласие со сроком аренды теряется | явное разделение решения о сотрудничестве и фактов об объекте |
| F03: ответ не на языке собственника | классификация language + локализованные фразы |
| F04: lock busy дедуплицирует собственный повтор | новый token/jobId при пересоздании |
| F05: сбой считается completed, pending остаётся без worker | настоящий failed job, сканирование orphan, backoff и ручная проверка |
| F06: redelivery не восстанавливает failed proxy | retry существующего failed ID + ограниченные фоновые повторы |
| F07: placeholder аудио закрывает расшифровку | merge по message ID с точным текстом каждого аудио |
| F08: секунды смешаны с миллисекундами | нормализация ingress и старой локальной истории |
| F09: ручной ответ с телефона не останавливает бота | любой unmarked phone outgoing = постоянная пауза Redis; marked initial outreach исключён |
| F10: неисправности и handoff не видны оператору | private manual Interaction, список/баннер CRM, частное уведомление, recovery counters в ready |
| applied:false игнорируется | прекращение текущего batch без ложного успеха |
| неоднозначное «да» становится согласием | уточняющий вопрос до записи статуса |
| сервис резервирует слишком большой ответ | cooperation request: max_tokens ≤512, temperature=0 |
| временная кредитная резервация HTTP402 считается постоянной | in-flight reservation повторяется; обычная нехватка средств требует проверки |
| recovery ID содержит недопустимый для CRM символ @ | стабильный SHA-256 issueId для pending без batch ID |

## Проверка

- Batymi: 259 тестов прошли, включая реальные Redis/BullMQ на отдельном
  временном Redis. Typecheck и build прошли. Обычные тесты используют заглушку
  LLM и не расходуют OpenRouter. Redis тесты не обращаются к модели.
- CRM: 97 целевых тестов webhook/status/review/instances/dispatch/chat прошли.
  Контроллер чата дополнительно проверен существующими Node-проверками гонок
  и выбора отправленных сообщений; JavaScript и Jinja проходят синтаксическую проверку.
- Пять ключевых синтетических сценариев с реальной production-моделью прошли:
  `explain_service`, `lease_en`, `lease_contract`, `consent_lease`,
  `initial_bare_yes`. См. `repair-critical-results.jsonl`.
- Более широкие платные проверки показали периодические HTTP402. У общего
  счёта OpenRouter на момент проверки оставалось около $0.26. Это внешнее
  ограничение, которое исправление кода не пополняет. Повторные широкие
  платные прогоны остановлены; их результат нельзя объявлять полностью успешным.
- `REVISION.md`, старые reproductions и старые semantic-results — снимок
  исходной ревизии до исправлений. Они специально показывают исходные ошибки
  и не являются актуальным acceptance suite.

## Границы проверки

Не отправлялись тестовые WhatsApp-сообщения собственникам. Автоматически
не возобновлялись старые остановленные диалоги. Локальные и синтетические
проверки подтверждают исправленные пути, но не дают гарантии любого будущего
ответа модели или доступности внешних сервисов. Остаток средств OpenRouter
требует пополнения для дальнейшей работы диалогов, использующих модель.

## Проверка установленной системы

CRM и Batymi обновлены через Coolify. На сервере `/health/ready` вернул 200:
Redis/queue/worker работают, активных линий две, режим `cooperation_only`,
planner `semantic_v3`. Контрольные SHA-256 четырёх установленных JS-модулей
(planner, service, recovery, provider) совпали с проверенной локальной сборкой.

`scripts/check-deployed-dialogue.cjs` прошёл прямо в установленном контейнере:
нормализованный webhook → объяснение услуги → согласие → тишина после согласия;
первоначальное «да» → один вопрос → отказ без LLM; ручной ответ → постоянная
пауза даже без записи в последних CRM-сообщениях. Все зависимости этого smoke
изолированы в памяти: 0 платных вызовов, 0 записей в рабочую CRM, 0 WhatsApp-отправок.

Четыре старых зависших active batches получили quarantine и запись ручной
проверки. Все четыре частных уведомления подтверждены как `sent`; issue IDs
валидны для CRM. Автоматическая очередь разговоров пустая: старые сообщения
владельцам не переотправлялись. Шесть ранее failed webhook-forward jobs
повторно доставлены в CRM; failed/waiting/delayed этой очереди равны нулю.
Временный Redis проверки и SSH-туннель удалены.

В браузере страница чата потребовала входа; визуальную проверку рабочего
авторизованного интерфейса не заявляем. Контракт API, шаблон и реальный
контроллер проверены автоматически. Повторный идентичный report не меняет
время создания проверки, а список можно раскрыть целиком без снятия паузы.
